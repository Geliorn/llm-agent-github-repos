# План: маппинг тегов и словарь задач

Статус: решения приняты в обсуждении 2026-10-13, код не начат. Словарь — `docs/tag-vocabulary-draft.md` (84 термина, черновик на согласование).

Реализуется **внутри `llm-agent-github-repos`**, отдельного плагина не будет (решение пользователя).

---

## 1. Задача

Сейчас в `post_tag` **3004 термина** на 668 репозиториев:

| | |
|---|---|
| с `count = 0` (сироты от переcбора) | 589 |
| с `count = 1` | 1753 |
| с `count ≥ 10` | ~110 |

78% тегов ведут на страницу с 0–1 записью. Словарь расщеплён синонимами: `mcp-server` 134 + `MCP` 112 + `model-context-protocol` 100 + `mcp` 14 — один смысл в четырёх ветках. Верх списка занимают **названия технологий** (`typescript` 65, `python` 53, `rust` 50), которые как навигация бесполезны и дублируют `repo_language`.

Причина в коде одна: всё, что не попало в topic правила, пишется в `post_tag` как есть — родные GitHub-topics плюс 1–3 тега, придуманные моделью ([class-lagr-collector.php:271](../plugins/llm-agent-github-repos/includes/class-lagr-collector.php:271), [class-lagr-llm-client.php:22](../plugins/llm-agent-github-repos/includes/class-lagr-llm-client.php:22)). Ни allowlist, ни нормализации, ни порога.

В плагине статей нужный механизм уже есть — `tags_mode = existing_only` ([class-laa-publisher.php:113](../plugins/llm-agent-articles/includes/class-laa-publisher.php:113)) с комментарием ровно про эту проблему. В GitHub-плагине его аналога нет.

## 2. Целевая модель: две оси

| Ось | Таксономия | Смысл | Сколько | Типы записей |
|---|---|---|---|---|
| **Разделы** | `repo_topic`, публичная | Класс инструмента: MCP · AI-агенты · Agent Skills | 3–10 | только `github_repo` |
| **Задачи** | `post_tag`, публичная | «Какую задачу решает» | 60–90 | `github_repo` + `post` + `contractor` |
| Факты | `repo_language`, `repo_license`, звёзды, свежесть, цена, условия | — | — | фильтры и бейджи, не навигация |

Схема повторяет референс otzyvmarketing.ru: категория + «Функции». Пересечение «раздел × задача» — фильтр внутри архива раздела.

**Главное правило: один термин — одна ось.** Имена разделов (`mcp`, `ai-agent`, `agent-skills`) в словарь задач не входят. Иначе `/repo-topic/mcp/` и `/tag/mcp/` — два URL с одинаковым содержимым: дубль, расщепление сигналов, непонятно, что продвигать. Технически: при утверждении термина проверяется, что такого нет в `repo_topic`, и наоборот.

**Решено отдельно:** `repo_topic` **не** подключается к `post`/`contractor` — это раздел каталога репозиториев, не раздел сайта. Сквозная связка трёх типов идёт только через `post_tag`. Если позже понадобится блок «статьи раздела» — это term-meta `_section_tags` (какие задачи относятся к разделу) и запрос по ним, без правки таксономий.

## 3. Статусы терминов

`_tag_status` ∈ `approved` | `candidate` | `merged`.

| Статус | Публичная страница | В облаке/меню | В sitemap | Записи привязаны |
|---|---|---|---|---|
| `approved` | да | да | да | да |
| `candidate` | нет (`noindex`) | нет | нет | **да** |
| `merged` | 301 на цель | нет | нет | нет (перенесены) |

Term-meta:

| Ключ | Содержимое |
|---|---|
| `_tag_status` | статус |
| `_tag_aliases` | строки, разрешающиеся в этот термин |
| `_tag_alias_candidates` | `{строка → счётчик}` — наблюдения для авто-алиаса, см. 5.4 |
| `_tag_proposal` | `{closest_existing, why, model, run_id}` — обоснование модели |
| `_tag_first_seen` | timestamp первой заявки |
| `_tag_proposed_count` | сколько раз предлагался (не равно `count` записей) |
| `_tag_reviewed_at` | когда человек последний раз смотрел |
| `_tag_merged_into` | term_id цели (только у `merged`) |
| `_tag_was_populated` | «записи когда-либо были» — защита свежеутверждённых от автопонижения, см. 7 |

Blocklist отклонённых — **option** `lagr_tag_blocklist` (хэши имён), не термины: отклонённый термин удаляется, хранить его в таксономии нечем.

## 4. Невидимость кандидатов

Делается явными точками, не одной — иначе кандидат утечёт в навигацию через саму запись:

- `get_terms` — фильтр по статусу (затрагивает `Agent_Catalog_Term_Grid`, `Agent_Catalog_Term_Links`, облако, сайдбар).
- `get_the_terms` / `the_terms` — список тегов на карточке и на single (`core/post-terms`).
- Архив термина — `noindex, nofollow` на `wp_head` (не 404: термин может быть утверждён завтра, и тогда страница должна появиться без возни с кэшем).
- `wp_sitemaps_taxonomies` / провайдер термов — исключение.
- Админка — **без** фильтров, там кандидаты должны быть видны.

## 5. Пайплайн маппинга

Вызывается из коллектора вместо нынешней записи топиков. Единая точка — `LAGR_Vocabulary::resolve( array $raw_terms, $post_id, $context )`.

### 5.1. Шаг 1 — детерминированная нормализация (без LLM)

Для каждой входящей строки по порядку:

1. Нормализация имени: lowercase, схлопывание пунктуации и пробелов. Хэш — по образцу `LAA_Topics::hash()` ([class-laa-topics.php:48](../plugins/llm-agent-articles/includes/class-laa-topics.php:48)).
2. Совпало с алиасом или именем **раздела** → отбросить (ось раздела уже проставлена из правила, дубль не нужен).
3. Совпало с blocklist → отбросить молча.
4. Совпало с `_tag_aliases` утверждённого термина → привязать термин.
5. Совпало со слагом/именем утверждённого термина → привязать.
6. Не разрешилось → в список «нераспознанных» для шага 2.

Если нераспознанных нет — **модель не вызывается вообще**. На текущих данных карта алиасов покрывает основную массу.

### 5.2. Шаг 2 — LLM, только для нераспознанного

Модель работает **с записью целиком**, а не «тег на тег»: на вход README-выжимка + все нераспознанные строки + словарь (84 термина, каждый **с однострочным определением задачи** — без определений модель матчит по похожести строк, что и дало текущие 3004 тега). 84 термина с определениями — порядка 1200 токенов, влезает целиком, RAG не нужен.

Формат ответа:

```json
{
  "tags": ["только из списка, 1-4"],
  "proposed": [{ "tag": "…", "closest_existing": "…", "why": "почему closest_existing не подходит" }]
}
```

Три возможных исхода для нераспознанной строки, и создание — самый редкий:

| Исход | Что делает модель | Что создаётся |
|---|---|---|
| Привязать к существующему | ставит термин в `tags` | ничего |
| Предложить новый | кладёт в `proposed` | кандидат |
| Проигнорировать | не возвращает ничего | ничего |

`closest_existing` + `why` обязательны — это и есть давление в сторону первого исхода: чтобы попасть в `proposed`, модель должна назвать ближайший существующий термин и объяснить, чем он не годится. Без этого поля модель уходит в изобретательство, потому что придумать новое всегда проще, чем выбрать.

### 5.3. Шаг 3 — валидация в PHP, а не в промпте

- Всё из `tags`, чего нет в словаре со статусом `approved` → **отброшено, не создано**.
- Для каждого элемента `proposed`: проверка blocklist, проверка по хэшу среди существующих терминов и алиасов.
  - уже предлагали → `_tag_proposed_count++`, новый термин не создаётся, запись привязывается к существующему кандидату;
  - впервые → создаётся термин со `candidate`, `_tag_proposal`, `_tag_first_seen`, привязывается к записи.
- Лимит новых кандидатов на прогон коллектора (настройка, по умолчанию 20) и на сутки. Сверх лимита — не создаём, пишем в `LAGR_Log`. Иначе один прогон по 50 репозиториям способен навалить 200 кандидатов и утопить очередь.

### 5.4. Авто-алиас из повторяющихся сопоставлений

Разница в последствиях, которую нельзя терять: шаг 1 — решение **постоянное** (алиас записан, модель больше не нужна), а исход «привязать к существующему» на шаге 2 — решение **разовое**: строка нигде не запомнилась, следующий репозиторий с тем же топиком снова пойдёт в модель, снова те же токены и с риском другого ответа. Самый частый и самый правильный исход ничему систему не учит.

Закрывается так:

- при исходе «привязать к существующему» строка пишется в `_tag_alias_candidates` термина со счётчиком;
- при счётчике **3** строка автоматически переезжает в `_tag_aliases`, с записью в лог.

Автоматически — потому что риск ограничен: добавление алиаса к уже утверждённому термину **не создаёт публичной страницы** и не меняет разметку существующих записей. Ошибочный алиас виден в карточке термина и снимается одним действием. Это принципиально иной уровень риска, чем автосоздание термина, где человек остаётся шлюзом.

### 5.5. Страховка на уровне таксономии

Хук `created_term` на `post_tag`: любой новый термин от **любого** писателя (коллектор, публикатор статей, ручной ввод, импорт, сторонний плагин) штампуется `candidate` и проверяется по blocklist.

Это ключевой элемент: enforcement работает глобально и не требует сотрудничества других плагинов. Достаточно того, что `llm-agent-github-repos` активен.

### 5.6. Подводный камень, проверенный на базе

Нормализация алиасов **обязана** идти до `wp_set_object_terms()`. Переписать имя на `pre_insert_term` нельзя: `wp_set_object_terms()` сначала делает `term_exists()`, не находит алиас, идёт в `wp_insert_term()`, фильтр переписывает имя на существующий канонический термин — и `wp_insert_term()` возвращает `WP_Error('term_exists')`, после чего **не присваивается ничего**. Проверено на локальной базе:

```
result: term_exists
assigned: []
alias-x created as its own term? no
```

Тег молча теряется — хуже, чем мусорный тег. Поэтому нормализация живёт в хелпере, который вызывают писатели, а `created_term` остаётся только страховкой.

## 6. Очередь «Теги: заявки»

- `WP_List_Table` поверх `get_terms( status = candidate )`. Прецеденты готовы: `LAA_Topics_List_Table`, `AUI_List_Table`.
- Колонки: термин · записей (`count`) · по скольким типам записей · обоснование модели · ближайший существующий · первая заявка.
- Сортировка по приоритету (см. 7).

**Почему не CPT и не своя таблица.** Кандидат уже проставлен записям в момент создания — отсюда и берётся «сколько записей его запросили»: это `$term->count`, который WP считает и поддерживает сам. В CPT или своей таблице этот список надо синхронизировать руками — на удалении записи, на переcборе, на ручной правке. Чем это кончается, в базе уже видно: 589 терминов с `count = 0` — рассинхрон там, где считал WP. Второй такой механизм будет врать так же.

Второй аргумент — утверждение: при статусе в term-meta «Утвердить» = переключение одного значения, термин уже есть, записи уже привязаны, переразметки нет. В варианте с CPT это «создать термин + переназначить N записей + удалить заявку», то есть второй путь записи, который может упасть на середине.

**Прецедент `LAA_Topics` — контракт переиспользуем, хранилище нет.** Тема статьи до публикации в WP не существует, её не на что повесить — там таблица единственный вариант. Предложенный тег существует как термин с момента проставления.

### Три действия

**Утвердить** — `_tag_status = approved`. Срабатывает мгновенно: записи уже привязаны, появляется публичная страница, термин встаёт в облако и sitemap.

**Склеить** — см. 6.1.

**Отклонить** — термин удаляется, хэш имени уходит в blocklist, модель больше его не предложит.

Плюс пакетный режим: выделить несколько кандидатов → «склеить все в …». Типовой сценарий — модель за месяц предложила 4 формулировки одной задачи.

### 6.1. Склейка

Два вида, различаются принципиально:

| Что склеиваем | Внешние ссылки | Что с термином после |
|---|---|---|
| `candidate` → `approved` | нет, страницы не существовало | удаляется сразу после переноса |
| `approved` → `approved` | есть: индексация, позиции, внешние ссылки | остаётся как `merged` и отдаёт 301 |

Отсюда и нужен третий статус `merged`: невидим, не в sitemap, но физически существует ради редиректа.

Порядок шагов важен именно такой:

1. Валидация: цель `approved`; цель ≠ источник; если цель сама `merged` — развернуть цепочку до финальной.
2. **Preview для человека:** сколько записей переедет, сколько из них уже несут цель, какие алиасы добавятся. Расклейки нет — решение необратимо, последствия показываем до нажатия.
3. Перенос записей: каждой записи источника добавить цель (append), снять источник. У записей, уже несущих цель, просто снимается источник — дубля не возникает.
4. Перенос алиасов: все `_tag_aliases` источника **плюс само имя источника и его слаг** переезжают в `_tag_aliases` цели.
5. `wp_update_term_count()` по обеим.
6. Источник: `candidate` → удалить; `approved` → `_tag_status = merged`, `_tag_merged_into`.
7. `LAGR_Log`: что, куда, сколько записей, кто инициировал.

Редирект: `template_redirect` на архиве термина `merged` → 301 на архив цели. Цепочки `A → B → C` разворачиваются по `_tag_merged_into` с ограничением глубины (5) и защитой от цикла. Без этого склейка превращается в генератор 404 по страницам, у которых уже был трафик.

Чего склейка не делает: не удаляет утверждённый термин, не склеивает в кандидата, не отменяется.

**Обратная связь на маппинг:** после склейки имя источника становится алиасом цели — следующий такой репозиторий разрешается на шаге 1 без вызова модели. Карта алиасов растёт от решений человека в очереди.

## 7. Регулятор

Недельный прогон. Запускается **внутри существующего** `lagr_tick_event` (10-минутный тик, [class-lagr-scheduler.php:35](../plugins/llm-agent-github-repos/includes/class-lagr-scheduler.php:35)) по guard-опции «когда был последний раз» — второй cron не регистрируем.

### Сигналы

| Сигнал | Откуда | Зачем |
|---|---|---|
| Масса | `$term->count` | базовая значимость |
| **Широта (кросс-тип)** | `GROUP BY post_type` по `term_relationships` | **главный критерий «задача или технология»**: не вышел за пределы репозиториев — не задача |
| Динамика | недельный снимок `count` (одна строка на термин в неделю) | растущая задача vs выдохшийся тренд |
| Спрос | запросы во внутреннем поиске (`class-search.php`), просмотры архива термина | кандидат, который **ищут**, должен прыгать в очередь |
| Избыточность | co-occurrence: доля записей A, несущих и B | автодетектор синонимов |
| Пустота | `count = 0` | мусор |

### Правила

Кандидат — **в начало очереди** (не в публикацию, человек остаётся шлюзом):

- `count ≥ 5` → «готов к ревью»;
- `count ≥ 3` **и** ≥2 типов записей → высокий приоритет;
- искали в поиске ≥ N раз → флаг приоритета.

Опционально — тумблер авто-утверждения (`count ≥ 15` и ≥2 типов), по умолчанию **выключен**.

Утверждённый — на склейку или вывод:

- `count = 0` 60 дней **и `_tag_was_populated`** → в кандидаты → затем удаление;
- `count < floor` 90 дней → предложить склейку, цель — самый часто сопутствующий более крупный утверждённый термин;
- избыточность ≥85% при заметно меньшем размере → предложить склейку с этим термином;
- **автоудаления утверждённого термина нет никогда** — у него могут быть внешние ссылки и позиции.

Флаг `_tag_was_populated` обязателен: ~⅓ словаря (бизнес и быт) заводится под будущие статьи и поставщиков, то есть с `count = 0`. Без флага первый же прогон снесёт свежеутверждённые термины, ещё не дождавшиеся контента.

### Коридор размера

Целевой коридор 60–90 утверждённых. Выше — регулятор поднимает `floor` и выносит больше предложений на склейку; ниже — снижает порог готовности к ревью, очередь двигается быстрее. Пороги становятся следствием одной внятной цели, а не угаданными числами. Это и есть «ручного аудита словаря не нужно».

### Ограничители

- Автоматика никогда не создаёт публичную страницу — кандидаты невидимы по построению.
- Автоматика никогда не удаляет термин, у которого есть записи.
- Каждое действие — в `LAGR_Log` с причиной, обратимо.
- Итог прогона — одна сводка в админке («3 кандидата готовы к ревью · 2 склейки предложены · 1 термин опустел»), а не ещё один дашборд.
- Co-occurrence — единственный тяжёлый запрос (self-join по `term_relationships`), кэшируется на неделю.

Включать регулятор **после** миграции: на текущих 3004 терминах он начнёт добросовестно регулировать сам мусор.

## 9. Интеграция с двумя другими плагинами

Enforcement глобальный (5.5), поэтому жёстких зависимостей нет ни в одну сторону.

- **`partner-catalog` — ноль правок.** Ввод ручной, автокомплит тег-бокса идёт через core-ajax `ajax-tag-search`, который фильтруется глобально из `LAGR_Vocabulary` — в боксе предлагаются только утверждённые.
- **`llm-agent-articles` — одна правка.** `tags_mode = existing_only` ищет через `get_term_by('name')` ([class-laa-publisher.php:120](../plugins/llm-agent-articles/includes/class-laa-publisher.php:120)), то есть матчит и кандидатов. Нужна точка расширения `apply_filters( 'laa_resolve_tags', $tags, $post_id )` в `LAA_Publisher::apply_terms()`, на которую подписывается `LAGR_Vocabulary`. Без GitHub-плагина фильтр ничего не делает — поведение прежнее. Конвенция «каждый плагин переносим отдельно» не нарушается: зависимости нет, есть хук.

## 11. Критерии готовности

- Утверждённых терминов в коридоре 60–90, кандидатов — сколько угодно, но ни один не виден на фронте.
- Доля репозиториев, размеченных без вызова модели (только шаг 1), — измеряется и растёт между прогонами.
- Ни один `post_tag`-термин не существует одновременно в `repo_topic`.
- Архив `merged`-термина отдаёт 301, а не 404.
- Деактивация плагина не портит данные (см. 13).

## 12. Открытые вопросы

1. **Продукты и экосистемы — отдельная ось или blocklist?** `claude-code` 115, `claude` 87, `codex` 53, `anthropic` 42, `openai` 33, `cursor` 31, `ollama`, `chatgpt`, `openrouter`. Как задача не формулируются, но «что работает с Claude Code» — осмысленный запрос, и это 5-й по частоте тег. Предложение: отдельная таксономия-фасет `repo_ecosystem` — **не** в навигацию и не в меню, только фильтр в архиве и строка на карточке. **Решить до миграции:** иначе 400+ привязок уйдут в blocklist безвозвратно.
2. **Гранулярность бизнес-групп словаря** — сейчас 4–9 терминов на группу. Направления, под которые уже есть пул поставщиков, имеет смысл детализировать сразу.
3. **Спрос как сигнал** — нужен ли учёт внутреннего поиска и просмотров архивов термов в первой версии регулятора, или отложить (это маленькая таблица по образцу `PC_Stats`).

## 13. Оговорки, которые надо занести в README плагина

- `llm-agent-github-repos` становится владельцем **сайтовой** сущности, а не только своей. Это цена отказа от отдельного плагина, принято осознанно.
- При деактивации плагина данные (статусы, алиасы, `merged`) остаются в term-meta, но enforcement выключается: новые теги снова публичны по умолчанию, а кандидаты становятся видимыми. При повторной активации всё работает снова. На деактивации ничего не чистить.
- Если появится `uninstall.php` (сейчас его нет) — он **не должен** удалять термины `post_tag` и их meta: это контент сайта, а не данные плагина.
- Словарь живёт в меню «GitHub-репозитории», хотя размечает и статьи. Чтобы редактор его находил — кнопка-ссылка на экране «Записи → Метки».
