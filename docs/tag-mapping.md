# Маппинг тегов: что реализовано

Версия плагина 0.8.0, 2026-10-14. Исходный план — [tag-mapping-plan.md](tag-mapping-plan.md), словарь — [tag-vocabulary-draft.md](tag-vocabulary-draft.md). Здесь — как это устроено в коде и где реализация отличается от плана.

## Решения, принятые перед реализацией (2026-10-14)

| Вопрос | Решение |
|---|---|
| Объём | весь план, включая регулятор |
| 12.1 Продукты и экосистемы (`claude-code`, `codex`, `ollama`…) | **в кандидаты**: записи сохраняются, из навигации и индекса уходят; решение про фасет откладывается |
| Словарь | черновик принят как есть, данные — `includes/lagr-vocabulary-seed.php`; в админке термины становятся обычными метками |
| `llm-agent-articles` | хук `laa_resolve_tags` + словарь в промпт плана статьи (`laa_tag_vocabulary`) |
| 12.3 Спрос (поиск, просмотры) | не делаем; регулятор работает только по числу записей |
| Свой промпт в настройках | блок словаря **дописывается всегда**, к любому промпту |
| WP-CLI | да, `wp github-repos tags …` |

## Пайплайн

```
GitHub topics ─┐
               ├─ шаг 1: LAGR_Vocabulary::resolve()   — без модели
               │    раздел (repo_topic) → отброшен
               │    blocklist          → отброшен
               │    алиас/имя/слаг утверждённого → термин
               │    остальное          → unresolved
               │
               ├─ шаг 2: модель (только если включена генерация описаний)
               │    в системный промпт дописан словарь с определениями
               │    + список unresolved; ответ: tags / mapped / proposed
               │
               └─ шаг 3: LAGR_Vocabulary::assign()    — валидация в PHP
                    tags      → только утверждённые, остальное выброшено
                    mapped    → привязка + счётчик в _tag_alias_candidates,
                                на 3-м совпадении строка становится алиасом
                    proposed  → blocklist? → уже есть кандидат (count++)?
                                → новый candidate (лимит 20/прогон, 100/сутки)
```

Ответ модели расширен полем **`mapped`** (`{"нераспознанная строка": "слаг"}`) — в плане его нет, но без него исход «привязать к существующему» нельзя связать с конкретной строкой, и авто-алиас (план 5.4) учить было бы нечему.

Если модель не вызывалась (генерация выключена или упала), нераспознанные топики по умолчанию становятся кандидатами (настройка «Нераспознанные топики без модели»: кандидаты / отбрасывать). Кандидаты невидимы, сигнал не теряется.

Модель вызывается вместе с генерацией описания — тот же запрос, отдельного вызова ради тегов нет. Отдельный `classify_tags()` используется только в `wp github-repos tags resolve --llm` для уже собранных записей.

## Статусы и невидимость

| Статус | Где видно |
|---|---|
| `approved` | везде |
| `candidate` | только в админке; на архиве — `noindex, nofollow` (не 404) |
| `merged` | нигде; архив отдаёт 301 на финальную цель (цепочки до 5, защита от цикла). Цель может быть разделом `repo_topic` |
| без статуса | старая метка до миграции — видна как раньше |

Фильтруются только **списочные** запросы (`get_terms` для облака, сетки, сайдбара, автокомплита тег-бокса `ajax-tag-search`, подсказок редактора блоков по REST `search`) и вывод `get_the_terms` на карточке. Поиски термина по `slug` / `name` / `include` / `object_ids`, cron и WP-CLI не фильтруются никогда: `term_exists()` внутри `wp_set_object_terms()` идёт через `get_terms()`, и фильтр там терял бы теги ровно так, как описано в плане (5.6). Кэш связей запись–термин тоже не трогается — он общий с админкой.

Страховка `created_term`: любая новая метка от любого писателя получает `candidate`. Имя из blocklist помечается и удаляется на `shutdown` — удалить прямо в хуке нельзя, вызывающий `wp_set_object_terms()` следом привязал бы запись к уже удалённому термину.

## Миграция

`wp github-repos tags migrate` (или кнопка на «Словаре задач») — только отчёт; применение — `--apply` / вторая кнопка.

1. Старые метки с `count = 0` — удаляются.
2. Засев словаря (84 утверждённых, алиасы разделов на термах `repo_topic`: `mcp`, `ai-agent`, `agent-skills`). Списки «слишком общие» и «языки/платформы» целиком уходят в blocklist.
3. Имена разделов (`mcp-server`, `ai-agents`, `skills`…) — записям-репозиториям проставляется раздел, если его не было; метка остаётся `merged` с 301 на архив раздела.
4. Слишком общие и языки/платформы — удаляются.
5. Совпавшие с алиасом — записи переезжают на термин словаря.
6. Остальное, включая продукты и экосистемы, — `candidate`.

**Отличие от плана (10.3):** склеенные старые метки не удаляются, а остаются `merged` с 301. Старые `/tag/…/` были публичными страницами, и план сам требует этого для склейки утверждённых (6.1). Цена — строки в `wp_terms`, невидимые на сайте.

Старая метка, чей слаг совпадает со слагом словаря (например `code-generation`), не склеивается, а превращается в термин словаря на месте: записи и URL сохраняются, старое имя становится алиасом.

После применения включается регулятор.

## Регулятор

Раз в неделю внутри `lagr_tick_event` (guard-опция `lagr_tag_regulator_last`), включается миграцией.

- Кандидат: `count ≥ 3` и ≥ 2 типов записей → «высокий»; `count ≥ 5` → «готов к ревью»; пустой дольше 90 дней → удаляется. Авто-утверждение (`≥ 15` и ≥ 2 типов) — тумблер, по умолчанию выключен.
- Утверждённый: пуст 60 дней **и** когда-то был непустым (`_tag_was_populated`) → в кандидаты; меньше порога 90 дней → предложение склейки с самым частым соседом крупнее; ≥ 85 % записей несут другой термин, который в 3+ раза больше → предложение склейки. Для терминов меньше порога детектор избыточности не применяется: одна запись тривиально «содержится» в любом соседнем теге.
- Коридор 60–90: выше — растёт порог, ниже — снижается порог «готов к ревью».
- Предложения склеек — в «Теги: заявки», подтверждает человек. Итог прогона — одна строка-сводка там же и в журнале.
- Еженедельные снимки `count` хранятся 13 недель (`lagr_tag_snapshots`); `LAGR_Tag_Regulator::trend()` пока нигде в правилах не участвует — это задел под «растущая задача / выдохшийся тренд».

## `llm-agent-articles`

Две точки расширения в том плагине, без зависимости в обе стороны:

- `apply_filters( 'laa_tag_vocabulary', '' )` в промпте плана статьи — модель выбирает теги из словаря;
- `apply_filters( 'laa_resolve_tags', null, $tags, $post_id, $tags_mode )` в `LAA_Publisher::apply_terms()` — подписчик возвращает id терминов. `existing_only` → только утверждённые; `llm` → неизвестные становятся кандидатами.

Без GitHub-плагина оба фильтра возвращают значение по умолчанию, поведение прежнее.

`partner-catalog` — без правок: его тег-бокс фильтруется через `ajax-tag-search`.

## Проверено

На WordPress 6.8.3 (SQLite) сценарием из 33 проверок: dry-run ничего не меняет; миграция по всем корзинам; шаг 1; валидация ответа модели; авто-алиас на 3-м совпадении; дедупликация заявок; страховка `created_term` и blocklist; склейка approved → approved с 301, цепочка A → B → C, склейка кандидата с удалением; отклонение; «одна ось» при утверждении. По HTTP: облако без кандидатов, `get_the_terms` без кандидатов, `noindex` у кандидата, 301 со склеенной метки на раздел и на термин, sitemap только из утверждённых, автокомплит тег-бокса без кандидатов, все экраны админки без PHP-предупреждений. Коллектор целиком — с подменёнными ответами GitHub и LLM.

Не проверено: живой LLM-провайдер (промпт проверен только по форме) и прогон на реальной базе из 3004 меток.
